# pi-simple-team tool API

Implemented API. Input signatures and agent-facing descriptions below are generated from the registered tools in the current source. Success behavior is verified by the tests and manual traces in [decision-trail.md](decision-trail.md).

The approved design is preserved in [review-approved.md](review-approved.md). All submitted annotations remain in [feedback.md](feedback.md), with their original locations in [annotation-locations.md](annotation-locations.md).

## Execution and identity rules

1. Spawn, resume, and add start work after every affected teammate is ready. `startIdle: true` leaves them idle.
2. `resumptionPrompt` adds a conversation message once. It does not change saved system prompts. With `startIdle: true`, no turn starts until a later message.
3. `teammateId` is the Pi session ID. Results do not duplicate it as `sessionId`.
4. An explicit team-wide Herdr setting overrides individual choices. Omission preserves individual choices. The dashboard identifies mixed transports.
5. Message success acknowledges publication, not completed delivery. A later failure is pushed to the original sender.
6. Status timestamps are generated by the extension and are output-only.

Kickoff names the teammate and restates its individual assignment so inherited main-agent history remains background. Cancellation during startup stops prepared members before automatic kickoff.

## Where prose is supplied

| Field | Destination | Purpose |
| --- | --- | --- |
| `promptSnippet` | Default system prompt, under Available tools | Short discovery hint |
| `description` | Callable tool definition | Invocation guidance |
| Parameter description | Input schema | Field meaning and constraints |
| `promptGuidelines` | Default system prompt, under Guidelines | Persistent general behavior rules; unused here |
| Result `instruction` | Successful tool result | Post-call guidance |

Descriptions and schemas normally accompany model requests before a tool is invoked. `promptGuidelines` is also early context, not progressive disclosure. Teammates use a custom system prompt, which bypasses the default snippet/guideline lists while retaining callable tool definitions.

The promptSnippet rule keeps discovery hints short. The MECE prose rule removes repeated instructions and places post-call guidance in results. Identical description/snippet text would appear once below. Differences are assessed as intentional or redundant, not claimed as historical fact.

## Shared types

```ts
type Teammate = {
  // Teammate name
  name: string;
  // Individual teammate system prompt
  systemPrompt: string;
  // Canonical provider/model id for this teammate. You should probably use one of these
  // user-scoped models: provider/model.
  model: string;
  // Thinking level for this teammate. Defaults to xhigh.
  // Schema: default: "xhigh".
  thinking?: "low" | "medium" | "high" | "xhigh" | "max";
  // Start with a clone of your context window rather than start fresh. Defaults to false.
  // Schema: default: false.
  inheritMainContext?: boolean;
  // Allow this teammate to create and manage teams of its own. Defaults to false.
  // Schema: default: false.
  canManageOwnTeams?: boolean;
  // Open a visible Herdr pane for this teammate. Defaults to false.
  // Schema: default: false.
  showOnHerdrPane?: boolean;
};

type TeamIdentity = { teamName: string; teamId: string };
type TeammateIdentity = { teammateName: string; teammateId: string }; // Pi session ID
type Status = { word: string; phrase: string; updated: string }; // ISO timestamp, automatic
type StatusMap = Record<string, Status>; // Participant names, including main

type StartResult = TeamIdentity & {
  started: boolean;
  teammates: TeammateIdentity[];
  instruction: string;
};

type MessageResult = TeamIdentity & {
  published: true;
  status: StatusMap;
  instruction: string;
};
```

The teammate input accepts only declared fields; obsolete optional names are rejected. Identity and session metadata from a full listing are output-only.

The scoped model ID `provider/model` above is a placeholder. Actual spawn schemas list the session’s scoped model IDs. Add uses the same Teammate fields with only the canonical-ID explanation on `model`.

When no scoped models exist, spawn appends this exact guidance to the model parameter:

> The user has not defined a list of preferred models explicitly. Figure out which model _you_ are by reading the value of the PI_PROVIDER, PI_MODEL, and PI_REASONING_LEVEL environment variables. That should give you something to start with. Confirm with the user before picking any model id.

## team_spawn

Available to: main, managing teammate.

```ts
team_spawn({
  // Name for the new team
  teamName: string;
  // Common system prompt for all teammates
  commonPrompt: string;
  // Teammates to spawn
  teammates: Teammate[];
  // Open visible Herdr panes for the team. Overrides individual teammate Herdr settings when
  // explicitly supplied. Defaults to false.
  // Schema: default: false.
  showOnHerdrPanes?: boolean;
  // Start teammates idle. Otherwise, start work following their common and individual system
  // prompts once everyone is ready.
  // Schema: default: false.
  startIdle?: boolean;
});
```

**description**

> You are automatically part of the team as main. Do not include yourself in teammates. Use team_resume to continue an existing team, or team_add_teammates to grow one.

**promptSnippet**

> Spawn a versatile team of agents.

**Difference assessment:** Intentional: the snippet invites discovery; the description explains automatic main membership and the relationship to resume/add.

**Success**

JSON text with `StartResult`. The teammate array contains the newly created members. No initial status map or separate sessions map. `started` is false for an idle or empty team.

**Failure**

Name/model validation, existing-team collision, session/registry, Herdr/startup, and partial kickoff failures. All extension-defined templates are listed below.

## Lifecycle success instructions

Spawn, resume, and add retain the bundled skill instruction, with runtime-resolved absolute paths:

> Read the bundled ai-to-leader skill at {absolute bundled ai-to-leader SKILL.md path} and the bundled ai-to-delegated skill at {absolute bundled ai-to-delegated SKILL.md path} in full before continuing, then follow their instructions.

When affected teammates start idle:

> These teammates are idle. Use team_send_message when you want them to start, with the instructions they need.

When affected teammates start work:

> Teammates will message you with milestones or requests for help. Avoid repeated status polling and shell sleeps. Set your status to explain what you expect from them. If you have no independent work, tell the user and end your turn. Ask the user whether to schedule progress checks every 15 minutes. If they agree, use schedule_reminder. After each check, schedule the next while the team needs oversight.

If no teammates are affected, only the bundled instruction is returned. The result does not promise progress from nonexistent work.

| `Message delivery failed for teammate "{name}" on team "{teamName}" (team ID: {teamId}). Original message: {message}. Cause: {cause}. Check the teammate’s status before retrying.` | Pushed to the original sender after a deferred failure. The actual message uses line breaks around the original content. |
| `Could not notify sender "{name}" of delivery failure: {cause}` | The sender could not receive its error notification. Logged without recursive notification. |
| `{ error: error.message }` | Internal HTTP catch handlers expose the underlying exception text. |

The model preflight error includes one line per unavailable model: `Model {JSON-quoted model} for teammate {JSON-quoted name} is not available.`

Callbacks can expose internal errors through an HTTP wrapper. Startup errors can also appear in stderr or team logs. Non-Error exceptions are converted with `String(error)`; other native exceptions pass through.

## Deferred by agreement

Expanded teammate-ID input acceptance, individual resumption-message objects, plural log filters, automatic resume on a spawn collision, and opt-in dormant listing remain deferred. The requested TODO comments for future changes are in the source. These are not unfinished parts of this implementation.
